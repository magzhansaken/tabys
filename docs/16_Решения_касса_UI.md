# ЧАСТЬ 16 — КАССА (Flutter): ЭКРАНЫ И ПРОТОКОЛ

Прочитано перед работой: **Wipon** desktop/sales (rounding, mixed-payment,
shift-close по трём сменам, quick-actions), web/reports/kkm-shifts;
**UMAG** «Продажи», «Возврат покупателя», «Отменённые товары», «Управление
кассами» (одноразовый ключ, настройка чека: заголовок/подвал/кодировка/ширина/
табличный вид/НДС); **МойСклад** «Отложенные чеки», «Работа на сенсорном
экране». Решения ядра приняты в части 4 — здесь они доведены до экранов
и до байтового контракта с сервером.

## 1. Архитектура приложения

```
pos/lib/
  main.dart                 маршрут = состояние: привязка → PIN → продажа
  core/api_client.dart      токен устройства в Keychain/Keystore, таймаут 4 с
  core/sync_engine.dart     Outbox → push батчами 100; pull дельт; WebSocket
  core/session.dart         устройство → кассир → смена → чек (вся логика)
  core/offline_auth.dart    PIN офлайн (bcrypt), блок перебора, approve старшего
  data/local_schema.dart    drift: каталог + чеки + смены + очередь
  domain/cart.dart          ВСЯ математика чека (одно место)
  domain/receipt.dart       ESC/POS с настройками чека (модель UMAG)
  features/                 pairing, pin, sale, payment, refund, shift
```

Правило одно: **экран рисует, база хранит, считает — domain/cart.dart.**
Формулы cart.dart зеркалятся Node-тестом part16.pos-app.e2e и прогоняются
против живого сервера — касса и кабинет не могут разойтись в копейках.

## 3. Решения экранов

1. **Экран продажи**: слева поиск (он же приёмник сканера) и плитка быстрых
   товаров, справа чек. Весовой штрихкод `22PPPPPWWWWWK` разбирается в
   строке поиска — кассир не вбивает вес руками (сценарий весов Rongta из
   Wipon).
2. **Оплата**: сегменты Наличные/Карта/QR/Смешанно/В долг. «В долг»
   физически неактивна без покупателя (правило Wipon). Кнопки номиналов —
   только те, что ≥ суммы чека. «Без сдачи» — отдельной кнопкой.
3. **Смена**: X-отчёт считается локально (у Wipon отчёты — только в
   онлайн-Консоли). Размен показан отдельной строкой от внесений —
   как в Z-отчёте ККМ. Закрытие с пересчётом: расхождение ≥ 1 ₸ требует
   комментария, и это правило работает офлайн.
4. **Возврат**: список чеков, «единожды по чеку» (правило UMAG), чек чужой
   смены — PIN старшего (журнал Approvals получает две подписи).
5. **Тёмная тема**: не слепит в зале, экономит батарею Sunmi.

## 4. Контракт с сервером (закреплён тестом part16)

- `POST /pos/pair` (код из кабинета) → токен → `GET /pos/bootstrap`
  (сотрудники с PIN-хэшами, профиль кассы) → `GET /pos/goods/catalog`
  (**новый эндпоинт**: полный снимок каталога + serverSeq одной транзакцией).
- Дельты: `GET /sync/pull?since=` — события `product`/`price`/`category`.
  **Закрыт пробел**: кабинет теперь пишет свои правки каталога в oplog
  (goods.service.emitToDevices) — раньше касса не узнала бы о новой цене.
- Офлайн-события: `shift` insert/**update** (закрытие офлайн — новый
  обработчик), `sale` (включая возврат отрицательным чеком с `refundOf`),
  `cancelled_item`, `cash_operation` (**новый обработчик**).

## 5. Починенные баги, найденные проверкой части

1. **PIN не сохранялся** при приёме сотрудника: setPin шёл отдельным
   подключением и не видел незакоммиченного сотрудника (скрытый баг части 15).
2. **Сотрудник без точки**: без явных storeIds кассир не попадал в bootstrap.
   Теперь по умолчанию привязка ко всем точкам.
3. **shift_totals** (миграция 024): наличные считались без вычета сдачи
   (дал 5000 при чеке 1025 → «в кассе 5000»), размен удваивался
   (поле смены + операция), возвраты офлайн/онлайн имели разный знак.
4. **Смена, закрытая офлайн, не закрывалась на сервере** — обработчик умел
   только открывать.
5. **Кассу нечем было создать**: добавлен `/admin/stores` +
   `/admin/stores/registers`.

## 6. Что сознательно отложено

  см. pos/README.md; контракт и математика проверяются Node-тестом.

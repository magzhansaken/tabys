# Часть 38 — Регистрация с подтверждением оператором

## Задача

Владелец: «пусть регистрируется с паролем, потом админ даст доступ».
Повод — СМС-шлюз в Казахстане требует договора, регистрации имени
отправителя и согласования шаблонов сообщений. Это недели, а запускаться
надо сейчас.

## Почему это не костыль, а хорошее решение

Для платного B2B модерация **лучше** автоматической СМС:

- владелец видит каждую заявку, звонит, знакомится, договаривается о цене;
- телефон проверяется живым звонком — надёжнее автоматического кода;
- нет расходов на СМС и зависимости от шлюза;
- так работает большинство B2B-сервисов на старте.

Так же поступают конкуренты: у UMAG и Wipon заявка с сайта → звонок
менеджера → подключение. Мы просто честно делаем это частью системы.

## Как устроено

1. **Регистрация без кода:** телефон, название магазина, имя, пароль.
   Плюс необязательный комментарий («магазин у дома, 2 кассы»).
2. **Статус аккаунта `pending`** — новый в перечислении статусов
   (`pending / trial / active / suspended / deleted`).
3. **Экран «Заявка принята»** — объясняет, что будет дальше, и сам
   проверяет статус каждые 20 секунд: как только оператор активирует,
   кабинет открывается без перезахода.
4. **Рабочие операции закрыты** одной проверкой в `PermissionsGuard`:
   «Аккаунт ожидает активации. Мы свяжемся с вами по указанному телефону».
   Одно место вместо проверок по всем модулям.
5. **Оператор** видит вкладку «Регистрации»: магазин, владелец, телефон
   (кликабельный для звонка), комментарий, время. Кнопка «Открыть доступ» →
   статус `trial`, пробный период 14 дней уже начислен при регистрации.

## Что добавлено сверх задачи (и почему обязательно)

**Сброс пароля оператором.** Восстановление пароля тоже шло по СМС. Без
замены забытый пароль означал бы **потерю доступа навсегда** — клиенту
некуда обратиться. Теперь оператор задаёт новый пароль и передаёт лично.

**Режим СМС сохранён целиком.** `REQUIRE_OTP=1` возвращает автоматику без
переделок. И это проверено **по-настоящему**: тест поднимает второй сервер
в режиме СМС и убеждается, что без кода регистрация отклоняется, а с кодом
проходит. (Первая версия теста была заглушкой `ok(true)` — переделал, такое
недопустимо.)

**Умолчание безопасное.** Модерация включена везде, кроме тестов:
`MODERATE_SIGNUP=1/0`, по умолчанию — включена, если `NODE_ENV != test`.
Иначе забытая переменная на новом сервере открыла бы свободную регистрацию.

## Что сделано
- Миграция `044_pending_registration.sql`: статус `pending`, поля
  `activated_at/activated_by/signup_note`; функции `operator_signups`,
  `operator_activate`, `operator_reset_owner_password` (SECURITY DEFINER —
  оператор живёт вне магазинов, построчная защита его запросы не пропускает)
- `auth.service.ts`: код необязателен, статус `pending`, `accountStatus` в контексте
- `guards.ts`: блокировка рабочих операций для неактивированных
- `operator.module.ts`: заявки, активация, сброс пароля
- Кабинет: форма без поля кода, экран `/pending`, вкладка «Регистрации» у оператора

## Три ошибки, пойманные до сервера
1. Проверка формы требовала код ровно из 6 знаков — регистрация без кода
   отбивалась ещё до попадания в логику.
2. Смена статуса на `pending` молча не срабатывала: запрос шёл без контекста
   магазина и не видел строку из-за построчной защиты.
3. Оператор не видел заявки по той же причине — переключил на защищённые
   функции базы, как сделано для остальных операторских выборок.

## Границы (честно)
- Телефон не проверяется автоматически — его проверяет звонок оператора.
  При росте числа клиентов это станет узким местом, тогда подключаем СМС.
- Защита от потока фиктивных регистраций — только ограничение по номеру
  (один номер = один аккаунт). Если начнётся спам, добавим ограничение по
  скорости и капчу.

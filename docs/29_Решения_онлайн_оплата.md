# Часть 29 — Онлайн-оплата подписки

## Что разобрано (рынок KZ 2026, веб-поиск)

- **Kaspi Merchant API v2** (2026): создать счёт → клиент платит в Kaspi →
  **webhook «оплачено» с подписью HMAC-SHA256** → срабатывает логика. Есть
  тестовое окружение (эмуляция оплат без реальных денег).
- Стандартный flow эквайринга: invoice → оплата → webhook → пополнение.
- **>90% онлайн-платежей в Казахстане идут через Kaspi**; карта — второй канал.
- 13.5 млн активных пользователей Kaspi.kz — привычный интерфейс снижает
  брошенные корзины.

## Что было у нас (части 23, 27)

Тарифы, подписка (баланс, зафиксированная цена, статусы trial/active/grace/
readonly/frozen), billing_move, ручной `topup` и `charge`. Но пополнение было
«как будто оператор внёс вручную» — реального приёма денег не было.

## Наши решения и почему

### 1. Счёт (invoice) + webhook — flow Kaspi Merchant API
Клиент выбирает сумму → создаём счёт у провайдера → получаем ссылку/QR →
клиент платит → **webhook подтверждает** → баланс пополняется. Это ровно то,
как работает Kaspi Merchant API, и мы строим под него.

### 2. Идемпотентность — критично для платежей
Двойной webhook (провайдеры повторяют доставку при таймауте) **не должен
задваивать баланс**. Функция `apply_invoice_payment` проверяет: если счёт уже
`paid` — возвращает текущий баланс, не пополняет повторно. Проверено тестом:
webhook дважды → баланс остался 14 900, а не 29 800. Это главная защита
платёжного контура.

### 3. Проверка подписи webhook
Webhook приходит извне (публичный эндпоинт без токена), поэтому подлинность
проверяется подписью HMAC-SHA256 — как требует Kaspi. Неверная подпись →
отказ. Проверено: подделанная подпись отбита.

### 4. Поиск счёта через SECURITY DEFINER
Webhook не имеет tenant-контекста (`app.account_id` не установлен), а
`billing_invoice` под RLS. Функция `find_invoice_by_external` с SECURITY
DEFINER делает единственный безопасный поиск по паре провайдер+external_id,
затем оплата проводится уже в контексте аккаунта счёта. Аккуратно с RLS, без
дыр.

### 5. Автопродление — оператор не бегает за деньгами
Если включено и оплаченный период на исходе, сами выставляем счёт на месячную
цену. Проверено: баланс < цены → счёт выставлен; баланс хватает → не выставлен;
выключено → молчит.

### 6. Провайдеры абстрагированы
`mock` для тестов, `kaspi`/`card` — по договору (как фискальные провайдеры
части 23). Форма интеграции, идемпотентность, автопродление готовы; боевые
ключи Kaspi Merchant подключаются за день-два после договора мерчанта.

## Что сделано
- Миграция `035_billing_online.sql`: `billing_invoice`, `billing_payment_method`, поля автопродления; функции `apply_invoice_payment` (идемпотентная) и `find_invoice_by_external` (SECURITY DEFINER)
- `server/src/billing/payment.provider.ts`: интерфейс + Mock + Kaspi (каркас Merchant API v2 с HMAC)

- Эндпоинты `/billing/invoice`, `/billing/invoices`, `/billing/auto-renew`, `/billing/run-auto-renew`, публичный `/billing/payment-webhook/:provider`
- Кабинет: карточка «Пополнить онлайн» + переключатель автопродления в разделе «Подписка»

## Границы (честно)
- Боевой контракт Kaspi Merchant API (точные поля запроса/ответа) заполняется
  по договору мерчанта — в открытом доступе его нет, придумывать нельзя.
  Механика счёта, идемпотентность, подпись, автопродление готовы и
  протестированы на mock.
- Планировщик, который вызывает `runAutoRenew` при истечении периода —
  системный воркер (как charge), настраивается при деплое.
- Сохранение токена карты для рекуррентных списаний (`billing_payment_method`)
  — задел; боевая токенизация зависит от провайдера.

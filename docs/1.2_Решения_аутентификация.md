# ПОДЧАСТЬ 1.2 — АУТЕНТИФИКАЦИЯ, РОЛИ И ПРАВА: АНАЛИЗ И РЕШЕНИЯ

Дата: 16.07.2026. Прочитано перед решением:

- **UMAG**: «Пользователи» (создание пользователя, пароль, PIN кассы, бывшие
  пользователи, выдать доступ), «Управление кассами» (одноразовый ключ
  авторизации, подтверждение штрихкодом администратора).
- **Wipon**: settings/account (профиль, смена пароля, восстановление, удаление),

  desktop/installation (вход в кассу теми же логином-паролем),
  desktop/multi-account («Администратор смены», переключение без повторного входа).
- **МойСклад**: «Вход в аккаунт», «Восстановление пароля», «Проблемы со входом»,
  «Доступ для сотрудника поддержки», «Сотрудники» (системные роли),
  «Мобильное приложение» (вход по PIN и Face ID — только iOS).

## 1. Как входят в систему у троих

| | МойСклад | UMAG | Wipon |
|---|---|---|---|
| Логин кабинета | Логин + пароль (высылаются на почту) | **Телефон + пароль** (задаёт владелец при создании пользователя) | **Телефон + пароль** |
| Восстановление | «Забыли пароль?» → по электронной почте | ➖ в доке | «Забыли пароль?» через форму входа |
| Логин на кассе | Роль «Доступ только к точкам продаж»; в мобильном — **PIN и Face ID, только iOS** | **Флаг «вход на кассу» + PIN 4 цифры** | **Те же телефон и пароль**, что в кабинете |
| Привязка устройства | ➖ | **Одноразовый ключ, генерируется в кабинете** | ➖ (обычный логин) |
| Переключение сотрудников | Только iOS | ➖ | **«Администратор смены»: одна смена, переключение без повторного входа** |
| Подтверждение чужим правом | ➖ | **Скан штрихкода администратора** | ➖ |
| Доступ поддержке | Галочка «Доступ для сотрудников поддержки», только администратор | **«Выдать доступ» техспециалисту, с отзывом** | ➖ |
| Ограничение по местам | Кассиры списком в точке | **Список торговых точек у пользователя** | **Склад обязателен, иначе вход невозможен** |

**Что из этого следует.**

Wipon пускает на кассу по телефону и паролю от кабинета — то есть кассир
физически вводит на кассе учётку, у которой есть доступ к деньгам и отчётам,
а пароль от неё гуляет по магазину. UMAG сделал правильнее: пароль владельца
остаётся у владельца, кассир входит четырёхзначным PIN, а сама касса
привязывается к аккаунту одноразовым ключом. Мы берём модель UMAG и
усиливаем её тем, чего нет ни у кого из троих.

## 2. Наши решения

### 2.1 Два независимых входа

**Кабинет (владелец, администратор, бухгалтер):** телефон + пароль.
Пароль хранится как bcrypt-хэш (cost 12). Пары токенов:
- **access-токен** — JWT, живёт 15 минут, проверяется без обращения к БД;
- **refresh-токен** — 30 дней, хранится в БД хэшем, **с ротацией**: каждое
  обновление выдаёт новый и гасит старый. Если старый токен придёт повторно —
  это признак кражи, гасим всё семейство токенов и требуем вход заново.

**Касса:** двухфакторно по сути, но за две секунды на практике:
- **фактор владения** — само устройство, привязанное одноразовым ключом
  (модель UMAG); у него долгоживущий device-токен в защищённом хранилище ОС;
- **фактор знания** — PIN сотрудника, 4 цифры (модель UMAG).

PIN сам по себе бесполезен без привязанного устройства — украденный PIN не
даёт войти ни с телефона, ни из браузера. Поэтому короткий PIN здесь
безопасен, а кассир не мучается с паролем каждую смену.

### 2.2 Офлайн-вход — то, чего нет у конкурентов

В документации UMAG офлайн не упомянут ни разу; у Wipon фоновая
синхронизация прямо помечена как неработающая офлайн, а вход в Desktop
требует логина и пароля. Вопрос, который они обходят: **как кассир войдёт в
смену, если интернет упал ночью?**

Наше решение: хэши PIN сотрудников, их роли и разрешения кассы **лежат на
устройстве** (синхронизируются заранее). Вход и проверка прав идут локально.
Устройство не спрашивает сервер — оно уже знает ответ. Интернет нужен только
для обмена событиями, и его отсутствие не мешает продавать.

Защита: 5 неверных PIN подряд → блокировка ввода на 5 минут (локально,
работает и офлайн); все попытки пишутся в журнал и уезжают на сервер.

### 2.3 Подтверждение действия старшим (усиленный UMAG)

У UMAG: кассир жмёт «Возврат», система просит отсканировать штрихкод
администратора. Отличная идея — берём и расширяем:
- подтвердить можно **бейджем-штрихкодом или PIN** администратора (бейдж не
  всегда с собой);
- работает **офлайн**;
- операция пишется в журнал с двумя подписями: кто выполнил и кто разрешил.
  При споре с кассиром владелец видит, кто именно санкционировал возврат.

### 2.4 Переключение кассиров (модель Wipon, ускоренная)

У Wipon «Администратор смены» переключается между сотрудниками без повторной
авторизации — удобно, но означает, что за него могут работать чужими руками.
Наш вариант: одна смена, переключение между кассирами **по PIN за две
секунды**, каждая операция подписана тем, кто её реально сделал. Флаг
«администратор смены» берём (у владельца включён всегда и не снимается —
как у Wipon).

### 2.5 Восстановление и первый вход

МойСклад восстанавливает через почту — в Казахстане у половины владельцев
магазинов почты нет или она заброшена. Значит: **SMS-код на телефон** (OTP,
6 цифр, живёт 5 минут, не больше 3 запросов в час на номер).
Сотрудников заводит владелец и сразу задаёт им пароль (как у UMAG) —
SMS на каждого продавца стоили бы денег и времени.

### 2.6 Матрица прав

Разделы соответствуют частям плана: главная, товары, склад, касса, продажи,
закупки, контрагенты, финансы, отчёты, документы КЗ, лояльность, сотрудники,
устройства, настройки. Действия: смотреть / создавать / изменять / удалять —
одинаково у всех троих, спорить не с чем.

Сверх матрицы — точечные флаги, каждый взят из конкретной боли:
- `can_see_purchase_price` — прятать закупочные цены (UMAG);
- `can_see_revenue` — прятать выручку и средний чек от кассира (Wipon);
- ограничение по торговым точкам (UMAG) — сотрудник видит только свои.

Проверка прав живёт **в одном месте на сервере** (guard) и **дублируется на
кассе** для офлайна. Правило: сервер — истина, касса — быстрый ответ.

### 2.7 «Выдать доступ» поддержке (UMAG) — наш ответ на их же боль

Главная жалоба клиентов UMAG — не дозвониться в поддержку. Наш ход: владелец
жмёт «Выдать доступ», указывает срок; наш специалист входит **под своим
аккаунтом**, видит чужой магазин, чинит. Все его действия помечены в журнале
как «сделано поддержкой», доступ отзывается кнопкой и гаснет сам по сроку.
Пароль клиента при этом никто не спрашивает — в отличие от «продиктуйте
пароль» по телефону.

## 3. Что сознательно НЕ делаем

- **Вход на кассу по логину и паролю от кабинета** (как Wipon) — это утечка
  учётки владельца в торговый зал.
- **Восстановление только по почте** (как МойСклад) — не для нашего рынка.
- **SMS на каждого сотрудника** — деньги на ветер, пароль задаёт владелец.
- **Face ID / отпечаток** — приятно, но это не то, что решает боль магазина;
  вернёмся в Части 14, задел в схеме оставлен.
- **Сквозная авторизация с 1С** (есть у МС) — в Казахстане у магазинов у дома
  1С почти нет; если понадобится — Часть 12 (интеграции).

## 4. Технические решения

| Решение | Почему |
|---|---|
| JWT для access, БД для refresh | Быстрая проверка без БД + возможность отозвать доступ мгновенно |
| Ротация refresh-токенов + детект переиспользования | Кража токена обнаруживается автоматически |
| bcrypt cost 12 для паролей и PIN | Медленный хэш = перебор PIN бессмысленен даже при краже базы |
| PIN уникален в пределах аккаунта | Иначе два кассира с PIN 1234 — и подписи операций врут |
| Токен устройства — не JWT, а случайная строка в БД | Устройство живёт годами; JWT такой срок держать нельзя |
| Журнал попыток входа (login_attempt) | Блокировка перебора + владелец видит, кто ломился |
| Проверка прав — один guard на сервере | Права в 14 модулях, размазанные проверки = дыра |

### Проверка: 47 автотестов по HTTP на живом сервере и живой БД

Поднимается настоящий сервер, запросы идут по HTTP, база — PostgreSQL под
ролью `shop_app` с включённым RLS. Покрыто: SMS-код и лимит запросов; регистрация;
вход и отказы; блокировка после 5 неудач; ротация refresh и детект кражи с
гашением семейства; смена пароля; уникальность PIN; запрет входа кассира в
кабинет; одноразовость ключа привязки; bootstrap с хэшами PIN для офлайна;
вход и переключение по PIN; подтверждение возврата PIN владельца и отказ
кассиру; права; выдача и отзыв доступа поддержке; мультитенантность.

### Дефекты, найденные проверкой (и почему это важно)

1. **Защита от перебора не работала.** Счётчик попыток читал `login_attempt`
   до установки контекста тенанта — RLS отдавал 0 строк, и блокировка молча
   не срабатывала. Исправлено узкими SECURITY DEFINER функциями (`auth_*`).
2. **Проверка уникальности PIN всегда говорила «свободен».** Та же причина:
   функция читала `employee` через RLS без контекста. Исправлено.
3. **Чужой аккаунт мог выдать ключ привязки к нашей кассе.** RLS проверяет
   владельца создаваемой строки, но не проверяет чужие ссылки в ней.
   Добавлена явная проверка принадлежности кассы аккаунту.

Все три — из категории «тихих»: код выглядел рабочим, тесты по счастливому
пути проходили бы, а дыра уехала бы в продакшен.

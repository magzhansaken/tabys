## 1. ГЛАВНОЕ: метод себестоимости — задание нужно поправить

В задании написано «средневзвешенная, как у всех троих». **Это не так, и
проверка документации это доказала:**

- **МойСклад**, статья «Себестоимость товара»: *«Себестоимость считается по
  принципу FIFO (первым пришёл — первым ушёл). Если текущий остаток товара
  был сформирован несколькими закупками с разной ценой, то при продаже в
  первую очередь будет списан товар из самой ранней приемки»*.
- **UMAG**, «Оприходование»: *«Во время проведения документа цена может
  поменяться на цену по методу FIFO»*. И в «Инвентаризации»: *«Программа
  посчитает итоги по методу FIFO»*.
- **Wipon**: метод в документации не описан вовсе (себестоимость упомянута
  только для составного товара — складывается из компонентов).

То есть **оба задокументированных конкурента считают по FIFO**.

### И всё-таки мы берём средневзвешенную. Вот почему

FIFO требует, чтобы документы шли строго по порядку. МойСклад пишет об этом
прямо: *«важно, чтобы документ закупки всегда был раньше, чем документ
продажи. В противном случае это будет продажа отсутствующего товара и
себестоимость у него будет нулевая»*. У них из-за этого целые статьи в
поддержке: «Почему себестоимость товара равна нулю» и «Если остатки
считаются неверно».

**А теперь вспомним нашу архитектуру.** Касса работает офлайн (Часть 1) и
отдаёт события позже — иногда через часы. Продажа, сделанная в 14:03, может
приехать на сервер в 19:00 — после приёмки, оформленной в 17:00. При FIFO
это означало бы регулярную нулевую себестоимость и вечные звонки в поддержку.

**Средневзвешенная скользящая** к порядку прихода событий устойчива: она
пересчитывает среднюю цену остатка при каждом приходе, и результат не
зависит от того, в каком порядке доехали продажи. Для магазина у дома это
ещё и понятнее: «в среднем пачка обошлась в 380 ₸».

Партионный учёт при этом никуда не девается — он нужен для сроков годности
(молоко, хлеб), и это отдельная механика, не метод оценки.

**Итог:** средневзвешенная как в задании — но не «как у всех троих», а
вопреки обоим, и по причине, которой у них нет: у них касса не работает
офлайн так, как у нас.

## 3. Инвентаризация: берём модель UMAG целиком

Их статья на 507 строк — самая проработанная вещь во всей их документации,
и там есть находки, которых нет у других:

| Находка UMAG | Берём? |
|---|---|
| **Остаток фиксируется на момент ПЕРВОГО сканирования товара** | ✅ **главное**: магазин продолжает торговать во время пересчёта, и продажи не портят результат |
| Статусы: Черновик → Подсчёт → Проведение → Проведён | ✅ черновик не влияет на учёт |
| Товары с одинаковым штрихкодом суммируются | ✅ |
| **Объединение черновиков** (несколько устройств / по зонам) | ✅ считают втроём — потом объединили |
| 5 способов добавить: поиск, сканер, из номенклатуры, создать новый, импорт | ✅ (создание товара прямо в пересчёте — важно: нашли неучтённое) |
| «Добавить из не отсканированных» + массовое обнуление | ✅ то, что не нашли — ноль |
| Валидационные ошибки до проведения (нет цены, штрихкод не найден, дополнительный штрихкод) | ✅ |
| Недостача = разница × закупочная цена; излишки приходуются | ✅ |
| Удаление только в черновике + восстановление | ✅ |
| ⚠ «Перед проведением кассы должны быть синхронизированы, иначе остатки могут быть неточными» | ❌ **не воспроизводим** — у нас `sync_readiness` из 1.3 знает точно |

**Наши добавления:**
1. **Слепой пересчёт** — кассир не видит учётный остаток, пока не введёт факт.
   Иначе человек видит «10» и пишет «10», не считая. Ни у кого из троих этого
   нет, а это единственный способ сделать инвентаризацию честной.
2. **Блокировка проведения при недоехавших событиях** — вместо предупреждения
   UMAG система прямо говорит: «касса №2 не отдала 3 события, подождите».

## 5. Что сознательно НЕ делаем

- **FIFO** — обоснование выше: наша касса работает офлайн, порядок событий
  не гарантирован.
- **Резервы под заказы** — Часть 4.
- **Производство** — вертикаль №2 (общепит).
- **Требовать ручной проверки синхронизации перед инвентаризацией** (UMAG) —
  у нас это знает система.

## 7. ПРОВЕРКА: 43 автотеста на живой базе (test/stock.e2e.js)

**Критерий Части 3 — полный товарный цикл без кассы — пройден:**
приёмка (в том числе блоками) → пересчёт средневзвешенной → накладные
расходы → перемещение между складами → списание → возврат поставщику →
оприходование → критические остатки → инвентаризация (слепая, со снимком
остатка, с обнулением и объединением черновиков) → отчёт недостачи →
проведение → пересчёт остатка из движений.

Ключевые проверки:
- **средневзвешенная**: (120×380 + 80×450)/200 = **408 ₸**;
- **накладные расходы**: 2000 ₸ доставки на 50 кг → средняя 620 ₸;
- **снимок остатка**: во время пересчёта продали 2 шт — снимок остался 5,
  и корректировка легла на разницу, а не затёрла факт;
- **перенос себестоимости** при перемещении: на рынке те же 408 ₸;
- **пересборка остатка** из движений после порчи значения.

**Регрессия:** полный прогон проекта — **271 пройдено, 0 провалено**.

## 8. Дефекты, найденные проверкой

1. **Тип параметра в снимке остатка** — Postgres не мог вывести тип, вставка
   позиции падала.
2. **Обновление закупочной цены** при приёмке — та же причина.
3. **Настройка «минус на складе» менялась в обход RLS** (ошибка теста, не
   кода) — и это лишний раз подтвердило, что защита на уровне БД работает:
   запись без контекста клиента просто не прошла.

## 3.7 Уведомления о критических остатках

| | МойСклад | UMAG | Wipon |
|---|---|---|---|
| Порог | «Неснижаемый остаток» в карточке, у товаров и модификаций | «Критический остаток» в карточке | ➖ |
| Уведомление | настройка «на телефон или электронную почту» в настройках пользователя | **каждое утро в 9:00**, со ссылкой на склад с включённым фильтром | ➖ |
| Фильтр | отчёт «Остатки» | ползунок «Ниже критического остатка» | ➖ |
| **Пополнение** | **✅ кнопка «Пополнить резервы» → внутренний заказ с позициями ниже минимума; дальше заказ поставщику или перемещение с другого склада** | ➖ | ➖ |

### Наши решения

1. **Время уведомления настраивается**, а не жёстко 9:00 (UMAG). Магазин у
   дома открывается в 8, гипермаркет — в 10; владелец сам знает, когда ему
   удобно смотреть закупки.
2. **Не спамим одним и тем же.** Это главное, чего нет у UMAG: если товар
   кончился и его неделю не заказали, UMAG будет слать одно и то же письмо
   семь дней подряд. Так уведомления отключают — и потом не узнают о
   действительно важном. Мы шлём, когда список **изменился**, а повтор без
   изменений — не чаще чем раз в заданное число дней.
3. **Пополнение до минимума — модель МоегоСклада.** Считаем, сколько
   докупить, и сразу предлагаем два пути: заказ поставщику (Часть 6) или
   перемещение с другого склада, где излишек, — второе доступно уже сейчас.
4. **Ссылка ведёт на готовый фильтр** (находка UMAG) — владелец не ищет,
   где это смотреть.

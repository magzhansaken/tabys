## 1. Дашборд: эталон UMAG «Главная»

Их страница устроена так:

| Блок | Содержание |
|---|---|
| Показатели за день | Выручка, Количество продаж, **Средний чек = Выручка / Количество продаж**, Себестоимость, **Валовая прибыль = Выручка − Себестоимость** |
| Выбор точек | несколько торговых точек сразу + валюта |
| График выручки | за период, с суммой за каждый день |
| Таблица «Счета» | магазин, название счёта, сумма, **разрешён ли отрицательный баланс** |
| Таблица «Синхронизация с сервером» | касса, магазин, **статус светофором** (красный / жёлтый / зелёный), время синхронизации |
| Таблица «Последние изменения» | магазин, документ, статус проведения, дата создания, дата изменения, пользователь |

Берём структуру целиком — она правильная. Три поправки:

### 1.1 Средний чек: у UMAG формула противоречит определению

В их же статье:
> **Количество продаж** — это количество проданных товаров или услуг.
> **Средний чек** рассчитывается по формуле: Средний чек = Выручка / Количество продаж.

Если «количество продаж» — это штуки товара, то деление даёт **среднюю цену
позиции**, а не средний чек. Продали 100 бутылок воды в 20 чеках — «средний
чек» по такой формуле выйдет в пять раз меньше настоящего.

У нас две разные величины, обе на дашборде: **чеки** (сколько покупателей) и
**позиции** (сколько штук). Средний чек = Выручка / Количество чеков.
Дополнительно даём **среднее число позиций в чеке** — это то, что показывает,
работает ли допродажа.

### 1.2 «Разрешён ли отрицательный баланс» — берём как осознанную настройку

Часть 7 закончилась тем, что касса ушла в минус и система предупредила.
Оказывается, UMAG держит на счёте флаг «разрешён отрицательный баланс».
Это разумно: у банковского счёта бывает овердрафт, у наличной кассы —
не бывает никогда. Делаем так же, но по умолчанию запрещаем.

### 1.3 Дашборд живой

Задание: «1:1 сценарий Главной UMAG, **но живой**». У UMAG страницу надо
обновлять. У нас с 1.3 есть WebSocket и оповещение аккаунта — дашборд
подписывается и обновляет цифры сам, когда касса пробила чек.

## 2. Статистика продаж — пять разрезов UMAG

> 1) По товарам. 2) По чекам. 3) По категориям. 4) По поставщикам. 5) По покупателям.

Все пять берём. По товарам у них: количество продаж и возвратов, сумма
продаж, себестоимость, прибыль, **рентабельность**, **наценка**, штрихкод,
единица измерения.

## 3. ABC — модель UMAG, она сильнее обычной

Обычный ABC — одна ось. У UMAG **две оценки и свод**:

> Столбец «ABC по р/ц» — классификация по суммарным продажам в розничных ценах.
> Столбец «ABC по прибыли» — классификация по прибыли.
> «Свод» — комбинированная классификация по двум параметрам.

Это ценно: товар может быть **AC** — гонит выручку, но прибыли не даёт
(сигарета), или **CA** — продаётся редко, но с большой маржой. Границы
у них: A — 80%, B — 15%, C — 5%.

**Наше добавление:** к своду даём короткую подсказку словами. «AC — оборот
даёт, прибыль нет: проверьте закупочную цену» полезнее, чем две буквы.

## 4. Кассиры и смены

UMAG «Отчёты по кассирам» (строго помесячно): Имя, Сумма по отчётам, Сумма
по продажам, Безнал, Возврат, **Итого = Сумма продаж − сумма возвратов**.

UMAG «Отчёты по сменам»: Остаток на начало → Приход (продажи, внесения,
возвраты, переводы) → Расход (покупки, расходы, изъятия, переводы) →
Остаток на конец, «включая разницу, если есть».

Берём. **Наше добавление:** к кассиру добавляем то, чего у них нет и что
владельцу важнее всего — **расхождения по сменам** (сколько раз недостача,
на какую сумму) и **отменённые позиции** (журнал из Части 4). Это и есть
контроль персонала, ради которого отчёт открывают.

## 6. Мобильный режим владельца (8.7)

У UMAG «Показатели по магазинам» есть на Web, **iOS и Android** — это их
главная фишка: показатели магазина в кармане. У Wipon отчёты в мобильном
приложении тоже есть. Паритет обязателен: те же цифры, тот же дашборд.

**Решение:** отчёты считаются на сервере и отдаются одинаково всем клиентам.
Мобильный получает компактную сводку одним запросом, чтобы открывалась на
плохой связи в подвале магазина: одна поездка, а не десять.

## 7. Что сознательно НЕ делаем

- **Воронка продаж** (МС) — это про CRM, не про магазин у дома.
- **Юнит-экономика с рекламными расходами** (МС) — Часть 13, вместе с ИИ.
- **Валюты в дашборде** (UMAG выбирает валюту) — торгуем в тенге.
- **Настройка колонок отчёта** (МС, UMAG «⚙️») — Часть 12, вместе с кабинетом.

## 9. ПРОВЕРКА: 74 автотеста (test/reports.e2e.js)

Смоделирован день магазина: 12 чеков, где сигареты гонят оборот при наценке
2,7%, молоко даёт прибыль, сыр продаётся редко но с высокой маржой, жвачка не
даёт ничего. Затем возврат, внесение, закрытие смены с недостачей 200 ₸.

Проверено на живой базе:
- **средний чек**: 3 592 ₸ по нашей формуле против 695 ₸ по букве определения
  UMAG — разница в пять раз;
- **ABC**: сигареты «AC» с подсказкой «оборот даёт, прибыль нет: проверьте
  закупочную цену»; сыр по прибыли в группе A;
- **светофор синхронизации**: зелёный → жёлтый (10 мин) → красный (2 часа);
- **сводный отчёт ККМ** — все шесть пунктов списка Wipon, включая остаток на
  начало и конец и обороты по секциям, плюс печать на чековой ленте;
- **живой дашборд**: сервер толкает обновление сам;
- **мобильный владельца**: всё одним запросом, проблемы вынесены наверх;
- расхождения кассира попадают в отчёт с отметкой.

**Регрессия всего проекта: 601 пройден, 0 провалено.**
